### K-001：跨 DLL 传含 STL 成员对象导致运行时崩溃（2026-08-05）
- 现象：实例化渲染路径偶发崩溃。
- 根因：导出类持有 `std::vector` 成员，跨 DLL 模板实例化/CRT 布局不一致。
- 规则：R1（导出类不暴露 STL 成员）；容器移 .cpp / Pimpl / 显式访问器。
- 关联：`documents/DLL_STL_BOUNDARY.md`

### K-002：消费者 exe 直接使用未导出的模板特化 → LNK2019（2026-08-01）
- 现象：编辑器/游戏 exe 调 `AssetManager::Load<Material>` 链接失败。
- 根因：`AssetLoader<Material>`/`<VertexArray>` 特化未显式实例化导出（仅 `Mesh` 已导出）。
- 规则：跨 DLL 用模板特化必须 `DMGE_API` 显式实例化，或走 DLL 内门面。
- 关联：`documents/ENGINE_ROADMAP.md` 技术债节、kb/KB-05

- 规则：新 shader 双后端可用性要在 PB-03 验证矩阵里显式确认。
- 关联：`documents/VULKAN_BACKEND.md`

### K-009：per-frame 删除桶"总是入当前帧槽"在帧间销毁场景不安全（2026-10-03）
- 现象：per-frame deletion queue 按"销毁时 `m_CurrentFrame` 桶"入队，帧间销毁的资源仍可能 use-after-free。
- 根因：EndFrame 之后、下一帧 BeginFrame 之前销毁时，前后两帧（两个槽）都可能 pending；当前槽桶的下次 flush 只等当前槽 fence，**另一槽**的 pending 提交仍引用该资源。
- 规则：入桶用非对称规则 `DeletionBucketFor(frameStarted, currentFrame)`——录制中入当前槽桶、帧间入另一槽桶（`VulkanDeletionQueue.h` 有完整证明）；flush 固定在 `BeginFrame(slot b)` 的 `vkWaitForFences` 之后。改调度前先跑 `test_deletion_queue.cpp` 性质测试。
- 关联：`engine/src/DMGameEngine/Platform/Vulkan/VulkanDeletionQueue.h`、`engine/tests/test_deletion_queue.cpp`、`documents/VULKAN_FIXES.md` §10.2

### K-010：swapchain 重建在 `vkWaitForFences` 之前执行 → 销毁 in-flight 资源（2026-10-03）
- 现象：`BeginFrame` 先处理 `m_NeedsResize` 再等 fence，`RecreateSwapchain` 销毁旧 swapchain image / 旧格式 pipeline 时，in-flight 提交可能仍引用它们（spec 违例，validation 报 use-while-in-flight）。
- 根因：resize 路径与 acquire OUT_OF_DATE 路径都汇入 `RecreateSwapchain`，但该函数在帧同步等待之前被调用。
- 规则：低频的批量销毁路径（swapchain 重建、shader 卸载）直接 `vkDeviceWaitIdle` 再销毁即可，不必为它做精细分帧——resize 是罕见事件，停顿可接受；高频路径才用 per-frame deletion queue。
- 关联：`VulkanGraphicsContext::RecreateSwapchain`、`documents/VulkanBackendReview.md` A 项、`documents/VULKAN_FIXES.md` §10.1

### K-011：`ctest --test-dir <build>` 报 "No tests were found"（2026-10-03，render-agent 与 test-agent 独立发现，管理员合并）
- 现象：`DMGE_BUILD_TESTS=ON` 构建成功后，`ctest --test-dir build`（或 `cmake-build-debug`/`build-agent`）报 `No tests were found!!!` 且 **exit 0**——容易误判为"测试没跑也过了"（假绿）。

- 关联：`engine/CMakeLists.txt`（L430 `enable_testing()`）、`.github/workflows/ci.yml`、`.github/CI.md`
- 状态：**已于 2026-10-03 修复**（分支 `agent/test-agent/enable-testing-root`）——`enable_testing()` 已挪至根 CMakeLists.txt（`add_subdirectory(engine)` 之前），`.github/workflows/ci.yml`、`.github/CI.md`、`AGENTS.md` §4 的 ctest 命令已改回 `ctest --test-dir <build>`；根 build 目录现生成 `CTestTestfile.cmake`。本条原内容保留作历史记录与"exit 0 + No tests = 假绿"识别规则。

### K-012：SceneSerializer JSON 往返会丢"未注册进 AssetManager 的程序化网格"，不能当 Play 快照用（2026-10-03）
- 现象：编辑器做 Play mode 快照若走 `SceneSerializer::Save/Load` JSON 往返，默认场景的 Cube（`MakeCubeMesh` 程序化生成、无 `MeshAsset` UUID）在恢复后网格变 null、不渲染。

- 关联：`editor/src/SceneDuplicator.h`（文件头有完整论证）、`engine/src/DMGameEngine/Scene/SceneSerializer.cpp`、commit 22abb0a

### K-014：非交互会话（agent 沙箱/CI）无法创建 Vulkan surface，运行时验证要换路径（2026-10-03）
- 现象：agent 会话里跑任何 Vulkan 渲染程序（game/editor exe 或自写基准），`glfwCreateWindowSurface` 恒返回 `VK_ERROR_INITIALIZATION_FAILED (-3)`；隐藏窗口（`GLFW_VISIBLE=FALSE`）与显示窗口结果相同，禁沙箱也一样。实例创建、设备枚举均正常，只有 WSI surface 失败。
- 根因：surface 创建依赖交互式桌面会话；agent 进程不在可交互 window station。
- 规则：① 涉及 Vulkan **运行时**的验证（Validation Layer 场景、Profiler 取证）不能在 agent 会话完成，留"待人工跑 game/editor"并写明场景；需要量化数据时改用**无 surface 的独立 VkDevice 微基准**（instance 不挂 WSI 扩展即可建 device/queue/CB，足以测 descriptor/submit 路径的真实驱动开销）。② 顺带：`static_cast<uint64_t>(VkSampler)` 编译失败——本 SDK 头文件里非 dispatchable handle 是指针类型，跨句柄算 hash 用 `reinterpret_cast<uintptr_t>` 中转（两种类型定义下都合法）。
- 关联：`documents/VULKAN_FIXES.md` §11.3（微基准方法）、`engine/src/DMGameEngine/Platform/Vulkan/VulkanRendererAPI.cpp`（HashBoundTextures）
### K-015：引擎 install(EXPORT) 无法生成，find_package(DMGameEngine CONFIG) 不可用（2026-10-03）
- 现象：单独 configure 引擎（`cmake -S engine -B ...`）在 generate 步骤报 `CMake Error: install(EXPORT "DMGameEngineTargets" ...) includes target "DMGameEngine" which requires target "glm" that is not in any export set.`——引擎自身作为顶层工程都无法完成 configure；编辑器"导出可运行工程"若走 `find_package` 方案则没有可 find 的包。
- 根因：`DMGameEngine` 对 `glm`（add_subdirectory 目标，非命名空间目标）和 `EnTT::EnTT` 是 PUBLIC 链接，但这两个目标不在任何 export set 里；且 install 规则只装 `DMGameEngineTargets.cmake`，从未生成 `DMGameEngineConfig.cmake`（无 CMakePackageConfigHelpers）。聚合构建（根 CMakeLists add_subdirectory）下 install 块被 `CMAKE_SOURCE_DIR == CMAKE_CURRENT_SOURCE_DIR` 守卫跳过，所以平时从不暴露。
- 规则：消费者工程（编辑器导出模板、外部 game）现阶段一律用 `add_subdirectory(<engine 源码路径>)` 消费引擎，`DMGE_BUILD_TESTS=OFF` 关掉 FetchContent 依赖。修引擎 install 规则时需要：① PUBLIC 的第三方链接包 `$<BUILD_INTERFACE:...>` 或抽一个可导出的 `DMGameEngine::Headers` 接口目标；② 用 CMakePackageConfigHelpers 生成 Config/Version 文件并 install。在此之前的任何 find_package 模板都是死路。
- 关联：`engine/CMakeLists.txt`（install 规则节）、`editor/src/ProjectExporter.h`（文件头有完整论证）、editor-agent 2026-10-03 会话（standalone configure 复现记录）

### K-016：EntryPoint.h 的 main() 丢弃 argv，消费者要读命令行参数只能用 CRT 全局（2026-10-03）

### K-017：ImGui `GetContentRegionAvail()` 可返回负值，cast 成 uint32 变成巨大尺寸 → GL 断言炸进程（2026-10-03）
- 现象：编辑器启动后 1~2 秒内概率性（约 50%，取决于 dock 布局首帧状态/有无 imgui.ini）死亡：崩溃形式为 `glTexStorage2D` 的 `DMGE_GL_CALL` 断言（`DMGE_CORE_ASSERT` → `__debugbreak`，无调试器时进程直接被 WER 杀掉）或堆损坏 0xC0000374 / segfault。日志中伴随 `GL_INVALID_VALUE in glTexStorage2D`。
- 根因：`EditorLayer::DrawViewport` 里 `ImGui::GetContentRegionAvail()` 在 dock 布局未稳定的首几帧可返回**负值**；`static_cast<uint32_t>(-1.0f)` ≈ 43 亿，躲过了 `if (w > 0 && h > 0)` 守卫，直接进入 `OpenGLFrameBuffer::Resize` → `glTexStorage2D(…, 4294967295, …)` → GL 错误 → 断言。注意 `__debugbreak` 在无调试器时不是"断点"而是进程终止，且不经过 CRT report hook，难以捕获。
- 规则：① 任何 ImGui/平台 API 返回的**带符号尺寸在 cast 到无符号之前**必须先做符号与上限判断（负数 cast 后恒为正，`>0` 守卫形同虚设）；② `DMGE_GL_CALL` 的断言意味着"带 GL 错误继续运行"不可选——上游传入 GL 的尺寸必须在源头校验；③ 排查此类 flaky 崩溃的有效手段：VEH（`AddVectoredExceptionHandler`）+ `CaptureStackBackTrace`+`SymFromAddr` 落盘，能抓到 `__debugbreak`/AV 的真实调用栈；`__debugbreak` 与 fast-fail 会绕过 SEH/UEF，必须用 VEH。
- 关联：`editor/src/EditorLayer.cpp`（DrawViewport 尺寸守卫）、`engine/src/DMGameEngine/Platform/OpenGL/OpenGLFrameBuffer.cpp`（Resize 上限拒绝）、修复 commit 见 develop

### K-018：ImGui 1.92.9 WIP 后端 `ImGui_ImplGlfw_WndProc` 对 `bd->Context` 无空保护 → "No current context" 断言（2026-10-03）
- 现象：编辑器启动/关闭时序敏感场景下弹 1~3 次 `Assertion failed: GImGui != 0 && "No current context..."`（imgui.cpp GetIO），点掉弹窗后进程 abort。
- 根因：vendored ImGui（1.92.9 WIP）的 GLFW Win32 WndProc 钩子从窗口属性取 `bd` 后直接 `ImGui::GetIO(bd->Context)`，bd 或 Context 为空/过期（backend 未完全就绪或拆除中）时即断言；消息派发时机不由我们控制。
- 规则：① 已在 `imgui_impl_glfw.cpp` 的 WndProc 入口加 DMGE 补丁（bd/Context/current context 任一无效则转发到前一个 WndProc 或 DefWindowProc）——更新 vendored ImGui 时**需要重新套用此补丁**（补丁头有 `[DMGE patch]` 标记）；② 引擎侧 `ImGuiLayer::OnEvent` 也加了 context 空守卫；③ 跨模块持有"全局上下文指针"的资源，任何在消息/回调路径使用它的代码都必须先判空。
- 关联：`engine/dependencies/imgui/backends/imgui_impl_glfw.cpp`、`engine/src/DMGameEngine/ImGui/ImGuiLayer.cpp`、修复 commit 见 develop

### K-019：VkPipelineCache 用 pInitialData 种入落盘数据时，驱动可能直接拒绝——必须回退空缓存重建（2026-10-03）
- 现象：`vkCreatePipelineCache` 带 `pInitialData` 时，若 blob 对当前驱动不可用（文件被第三方截改、跨驱动版本残留等头校验查不出的损坏），调用返回非 `VK_SUCCESS`；若代码只走 `VK_CHECK`（记日志继续跑），`m_PipelineCache` 就是 `VK_NULL_HANDLE`，首次 `vkCreateGraphicsPipelines` 传 NULL cache 虽然合法，但缓存对象永远缺位，落盘功能静默失效，更糟的是后续按非空假设使用即崩。
- 根因：磁盘头校验（magic/版本/设备身份/UUID/长度）只能挡"文件层"损坏；驱动 blob 自身的兼容性只有驱动能判，`pInitialData` 被拒是合法路径而非异常。
- 规则：带 `pInitialData` 创建失败 → **用空参数重试一次**再 `VK_CHECK`；实现见 `VulkanRendererAPI::Init`。顺带：序列化/回读自研头格式时用 `static_assert(sizeof(Header)==...)` 防编译器插 padding；截断文件若头字段被清零，会先命中的是身份校验而非截断校验（微基准里验证过，别据此误判校验顺序错了）。
- 关联：`engine/src/DMGameEngine/Platform/Vulkan/VulkanRendererAPI.cpp`（Load/SavePipelineCacheData、Init）、`documents/VULKAN_FIXES.md` §12.2

### K-020：蒙皮导入沿用"节点变换烘焙"会破坏调色板数学——顶点空间必须留在 bind pose（2026-10-03）
- 现象：若按静态网格的既有套路把节点全局变换烘进顶点，蒙皮结果错乱：顶点被预变换到模型/世界空间，而 inverse bind 与动画层级在（bind pose 的）模型空间，两套空间不一致。
- 根因：蒙皮公式 palette(j) = world(j) * invBind(j) 定义在"顶点处于 bind pose 模型空间"上；assimp 的 aiBone->mOffsetMatrix 是 mesh→bone 空间，不补偿 mesh 节点自身的变换。
- 规则：蒙皮网格导入**不烘焙节点变换**（假定 mesh 节点全局变换 = 单位阵——标准蒙皮模型/simple_skin/animation_with_skeleton 均成立）；静态路径烘焙行为不变。将来要支持 mesh 节点自带变换的蒙皮模型时，需把该节点变换并入 invBind（或层级根）统一空间。
- 关联：`engine/src/DMGameEngine/Asset/MeshImporterAssimp.cpp`（ProcessNode bakeTransforms 分支）、`engine/src/DMGameEngine/Animation/AnimationMath.cpp`（ComputeSkinningPalette）、anim-agent 阶段1 commit c397209

### K-021：headless 测试不能构造 GPU 后端对象——`VertexArray::Create()` 直接 0xc0000005（2026-10-03）
- 现象：无 GL 上下文的 gtest 里 `VertexArray::Create()`，进程 SEH 0xc0000005（glad 在无上下文时调 glGenVertexArrays）。
- 根因：后端工厂无"无上下文"守卫，Create 即触 GL 调用；RenderQueue/Renderer 层测试因此只能覆盖 CPU 侧契约。
- 规则：headless 测试禁止构造 VertexBuffer/VertexArray/Texture/FrameBuffer/真 Shader 等后端对象；渲染路径测试只测纯数据结构（如 Renderable 调色板字段）或 Null 测试替身（先例 test_scene.cpp NullShader）；真 GPU 验证走人工运行（与 K-014 Vulkan surface 限制同理）。
- 关联：`engine/tests/test_animation_render.cpp`（文件头有完整论证）、kb/KB-07 K-014

### K-022：全局忽略规则会"静默吞掉"目录式 git add 的测试资产（2026-10-03）
- 现象：CI 上只有 Test 步骤失败（Configure/Build 全绿），本地却全绿；`git add engine/tests/assets/` 不报错，但远端 checkout 缺文件。
- 根因：根 .gitignore 的 `*.obj`（编译目标文件规则）把测试资产 `box.obj` 静默排除——`git add <目录>` 对目录内被忽略的文件不报错、直接跳过。硬编码绝对路径（`D:/CPPPractices/...`）同时掩盖了问题：本地文件存在所以测试全绿。

- 关联：`.gitignore`、`engine/tests/CMakeLists.txt`（DMGE_TEST_ASSETS_DIR）、CI 三跑修复记录（26c1664 全绿）

### K-023：`Shader::Create(name, vertSrc, fragSrc)` 不解析 `#type` 段——合并式源只能走 filepath（2026-10-04）
- 现象：把带 `#type vertex`/`#type fragment` 的合并源整体传给 `Shader::Create(name, vertexSrc, fragmentSrc)`，编译产物错乱（整段当单一 stage）。
- 根因：两参/三参源的构造函数把传入字符串直接当 vertex/fragment 各自的完整源码；只有 filepath 构造函数（OpenGLShader/VulkanShader 的 PreProcess）才解析 `#type` 分段。
- 规则：引擎内部用内嵌源码创建 shader 时必须**按 stage 拆分**传入（先例 `DeferredRendering.h` 的 `GBufferVS()/GBufferFS()` 等）；合并式 `.glsl` 文件仅作为 filepath 加载路径或人类可读参考副本，两处内容需保持同步。
- 关联：`engine/src/DMGameEngine/Renderer/Shader.cpp`（两个 Create 重载）、`Renderer/DeferredRendering.h`、kb/KB-03（Vulkan GLSL 限制）

### K-024：Vulkan pipeline 缓存键必须包含 colorAttachmentCount（MRT）——否则跨 pass 复用错管线（2026-10-04）
- 现象：引入 2 附件 G-buffer pass 后，同一 shader 在 1 附件（swapchain/editor FB）与 2 附件 pass 间切换，若 PipelineKey 只存单个 colorFormat，键可能碰撞或漏判，产生 attachment count mismatch（validation 报错/未定义行为）。
- 根因：`VkPipelineRenderingCreateInfo::colorAttachmentCount` 与 `VkPipelineColorBlendStateCreateInfo::attachmentCount` 都烘焙进 VkPipeline，是" pass 结构"的一部分，不只是格式。
- 规则：pipeline 缓存键必须包含**附件数 + 全部活动颜色格式**；比较与哈希只看前 N 个（N=附件数）活动项，未用尾部条目允许保留陈旧值（先例 `VulkanRendererAPI::PipelineKey`，含注释证明）。同理 GL 侧无此问题（状态机全局、glDrawBuffers 属 FBO 状态），但 MRT 下 blend 要显式关闭。
- 关联：`engine/src/DMGameEngine/Platform/Vulkan/VulkanRendererAPI.h/.cpp`、`documents/DEFERRED_RENDERING_DESIGN.md` §2
### K-025：D3D11 PS 输入可能按寄存器"序"而非语义链接——VS 输出必须先声明 varying 再声明 SV_Position（2026-10-04，d3d-agent）
- 现象：D3D11 后端 headless smoke 测试里，三角形几何/深度/清屏全部正确，但 PS 的唯一 varying 输入恒为 (0,0,0,1)（缺失属性的默认值）；独立 100 行教科书级最小复现程序（裸 D3D11CreateDevice + DrawIndexed + 硬编码 InputLayout）同样复现——**与本引擎代码无关**。CPU 侧逐层排除：VB 内容 staging 回读正确、InputLayout 创建成功且签名/语义与 VS 完全匹配、layout 元素换序会相应改变结果（layout 本身生效）。最终定位：**该机器的 D3D11 运行时（硬件驱动与 WARP 皆然）把 PS 输入寄存器 i 链接到 VS 输出寄存器 i（按序），而非按语义匹配**；编译器又把 `struct VSOut{ v_Position : SV_Position; v_Color : TEXCOORD0; }` 的 SV_Position 分配到寄存器 0，于是 PS 的 TEXCOORD0 输入拿到的是裁剪坐标。`FrontCounterClockwise`、编译开关（DEBUG/Optimize）、cbuffer 有无、语义改名（COLOR0/TEXCOORD1）均不改变该行为；把 varying 声明到 SV_Position **之前**（占寄存器 0）后立即恢复正常插值。
- 规则：① 本引擎所有 D3D11 HLSL 的 **VS 输出 struct 一律先声明所有 varying、最后声明 SV_Position**，且 **PS 输入 struct 保持与 VS 输出相同的成员顺序**（见 `Platform/DirectX/Shaders/BlinnPhong.hlsl` 头注释）——按序与按语义两种链接方式下都正确；② 排查"PS 输入恒为默认值"时，先用最小独立程序复现以区分引擎 bug 与环境/驱动行为；③ 本机无法安装 D3D11 SDK 调试层（Graphics Tools），无 info queue 可用，逐像素回读 + 顶点 staging 回读是最有效的取证组合；④ 该行为疑似与沙箱/VM 的显示驱动栈有关（`D3D_DRIVER_TYPE_REFERENCE` 在本机不可用，0x887a0004），真机 GPU 上未验证——阶段 B 接入真机时复测。
- 关联：`engine/tests/test_d3d11_smoke.cpp`（文件头注释）、`documents/DIRECTX_BACKEND_DESIGN.md` §3.3/§5、kb/KB-07 K-014（同类"agent 沙箱环境限制"）

### K-026：Vulkan 离屏附件 loadOp=Load 不能沿用 UNDEFINED 布局转移——UNDEFINED 无条件丢弃旧内容（2026-10-05，render-agent）
- 现象：未实际触发（本波所有调用点均 loadOp=Clear），是 RenderPassDesc 消费路径实现时主动规避的设计坑：离屏 pass 的布局转移代码原样写的是 `UNDEFINED -> COLOR/DEPTH_ATTACHMENT_OPTIMAL`，若把 loadOp 改成 Load（想保留上一 pass 的内容），UNDEFINED 转移会把内容丢掉，Load 静默变成"DontCare 语义"。
- 根因：`VK_IMAGE_LAYOUT_UNDEFINED` 的语义就是"previous contents not guaranteed"；想要 Load 必须从内容所在的真实布局转移。离屏 FBO 的颜色/深度附件在 `EndRenderPass` 后处于 `SHADER_READ_ONLY_OPTIMAL`，这正是 Load 路径的正确源布局。
- 规则：RenderPassDesc 消费路径（`VulkanRendererAPI::BeginRenderPass(desc)`）按 loadOp 选源布局——Clear/DontCare 用 UNDEFINED，Load 用 SHADER_READ_ONLY_OPTIMAL。**首次使用即 Load 是构造性非法**（新附件尚未渲染过，validation 会报 layout mismatch）——要支持"首次使用 Load"需在 VulkanFrameBuffer 记录每附件布局，属后续资源屏障抽象（2b）的活，勿在调用点 hack。
- 关联：`engine/src/DMGameEngine/Renderer/RenderPassDesc.h`、`engine/src/DMGameEngine/Platform/Vulkan/VulkanRendererAPI.cpp`（BeginRenderPass 注释）、`documents/DEFERRED_RENDERING_DESIGN.md` §7

### K-027：/W4 "零新增警告"核账的两个假象 + 导出 struct 里的 glm 成员必报 C4251（2026-10-05，render-agent）
- 现象：①增量构建 no-op（没重编译任何 TU）时 grep 警告得 0——是"没编译"不是"没警告"；②全量重建后出现 ~800 条/配置的 C4251 基线噪音（Light.h/Shader.h/Material.h 等既有导出结构的 STL 成员，OpenGL 与 Vulkan 配置都有），差点误判为本次改动引入。③新增 `RenderPassDesc`（DMGE_API）里放 `glm::vec4` 成员后，每个实例化 TU 报一条 C4251（glm 无 dll 接口）。
